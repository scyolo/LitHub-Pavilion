## 已定位的性能问题

在生产预览、全新 Chromium 上下文、无网络限速的优化前实测：

| 操作 | 冷加载到结果 | 卡片分片 | 实测响应正文 |
|---|---:|---:|---:|
| learning | 2,205 ms | 96 | 22,874,043 B |
| speculative decoding | 793 ms | 58 | 14,275,129 B |
| learning + ICML 2025 | 372 ms | 7 | 2,605,325 B |
| speculativ decodng | 881 ms | 58 | 15,799,343 B |

瓶颈并非只在网络请求速度：旧引擎必须加载所有候选的卡片后才能排序，常见词几乎触发整份卡片目录下载。旧的少量完整标题测试不能代表这种真实搜索负载。

## 修复方式

1. 新增版本绑定的紧凑排序/筛选索引：数字化词典、差分论文 ID、日期排序序号；不复制标题、摘要和 URL。
2. 倒排分桶由词项哈希的 2 位扩展到 3 位，并保存标题词项位置，保留短语、词项、模糊匹配优先级及全局 BM25 分数。
3. **先精确筛选、排序、分页，再加载当前页的卡片**；卡片分片从 4,000 条缩至 256 条。普通浏览也使用这一流程。
4. 旧版本快照仍走既有路径；新格式为外层 6 / 内层 5。完整论文详情仍只按打开的 ID 加载，首页不加载检索索引或论文分片。
5. 单次读取/检索配置 12 秒硬等待上限：停掉阻塞 Worker 和下载，展示明确错误与重试；超时不自动再等一轮。该上限是故障保护，不是所有设备/公网请求必定成功的承诺。
6. 首页覆盖矩阵先渲染 20 行，并明确提供展开全部 338 个来源的按钮；降低低端移动设备的首屏 DOM 成本，不改变总量或来源集合。
7. 修复 `.gitignore` 中通用 `coverage/` 规则误排除公开来源关联文件的问题。

## 验证方法与预算

- 夹具上对所有排序、过滤、AND、短语、完整 Unicode 标题、拼写/前缀进行新旧算法比对，并断言只下载当前页卡片。
- 完整数据集运行 `npm run check:snapshot-search`，检查每个标题身份和抽样搜索。
- `npm run check:snapshot-performance`：新旧算法在相同完整数据集上逐项对照；冷读取 ≤3 MiB、≤40 个请求，卡片分片数不超过当前页条数，热重复零新增请求。Node 处理预算冷 6 秒/热 1.5 秒，不冒充公网耗时。
- 浏览器弱网：`python scripts/benchmark_static_server.py frontend/dist --mbps 4 --latency-ms 80`。所有页面和 Worker 请求共享 **4 Mbps 总带宽**，每次响应额外延迟 80 ms，不是给每个请求独享 4 Mbps。文本使用 gzip，与生产静态托管更接近。
- 参考站实测使用其真实 GitHub Pages 网络，本站使用本机生产预览；两者传输条件和论文范围不同，不能把数字直接作网站速度排名。

## 验收结果

新快照已完成数据库逐公开字段一致性核验：**381,441** 条公开记录（2023–2026 年为 **381,433**，另保留 8 条更早记录），版本 3d798240bffdabc2ac5bc4d601610a03568e1327b7879db36e5417c600d33938。325 个直接来源、336/338 个直接或官网逐篇关联的来源；零直接来源—年份 142 个，合并关联后的零单元 **114** 个（本轮 117 → 114）。这些零单元不等于已证实漏采的论文清单。

- 后端 **892** 项测试通过；前端 **177** 项测试通过；生产构建、Ruff 和 diff 检查通过。
- 全部 **381,441** 个标题身份已核验；33 个完整标题、8 个自动模式、21 个跨方向、8 个非相邻 AND 检查通过。新旧算法在同库上的结果、分数、过滤和分页一致。
- 安装目录的 **6,614** 个引用资产哈希全部通过；体积 665,264,498 B，低于 800 MiB 发布预算。12 份当前来源关联文件的哈希也已核验。
- 首页仅 2 个快照元数据请求，479,101 B，零索引/论文分片，继续满足 512 KiB 元数据预算。浏览器页面总请求还包含 HTML、JS、CSS，不能与这两次数据请求混为一谈。

| 场景 | 本机冷加载 | 本机热重复 | 限速移动端冷加载 | 限速移动端热重复 |
|---|---:|---:|---:|---:|
| 首页 | 201 ms | 150 ms | 1520 ms | 933 ms |
| 论文列表 | 517 ms | 27 ms | 3944 ms | 146 ms |
| learning | 873 ms | 38 ms | 5469 ms | 171 ms |
| speculative decoding | 720 ms | 28 ms | 4684 ms | 302 ms |
| learning + ICML 2025 | 527 ms | 27 ms | 4893 ms | 339 ms |
| speculativ decodng（自动纠错） | 699 ms | 27 ms | 6048 ms | 317 ms |
| 完整标题 | 265 ms | 33 ms | 2870 ms | 466 ms |

限速移动端：390px、共享 4 Mbps、每响应额外 80 ms、主线程 4 倍 CPU 慢化；不是全部 Worker CPU 或真实手机硬件的等效模拟。冷加载包含导航、初始化及实际结果；热搜索为同会话重新访问相同查询。首页热加载还故意把 manifest 网络请求延迟 5 秒，已验证的概览不等待它。

最终 learning 响应正文为 1,751,474 B，相比优化前 22,874,043 B 降低约 92.3%。正常搜索没有加载完整详情/摘要分片。浏览器预算为本机首页 1 秒、冷搜索 1.5 秒；上述弱网主线程慢化环境为首页 2.5 秒、冷搜索 6.5 秒；全部通过。不能据此保证更慢网络或其他设备也在同一时间内完成。

故意阻塞索引时，12384 ms（包含导航）显示明确超时错误，只有 1 次阻塞请求，没有再次自动等待；点击“重新加载”后 939 ms 恢复结果。此测试曾发现论文页自行定义的重试规则覆盖了全局规则，现已抽为统一策略并补上回归测试。实键 Enter 搜索为 851 ms；本次自动化交互观察到的最大事件时长为 112 ms（不是完整现场 INP 分布）。新增来源年份、完整主副标题、原始 DOI、展开全部 338 来源和移动端无横向溢出均通过。

参考站默认 A 类会议语料为 107,635 篇：本次真实 GitHub Pages 冷首页 3033 ms、首次 learning 4046 ms、热重复 323 ms，首次全局索引响应约 4.02 MB。它与本机预览的网络条件和语料范围不同，这些数值只作加载策略参照，不构成公平速度排名。

**未完成的验证**：本机 Docker 守护进程未启动（缺少 dockerDesktopLinuxEngine 管道），因此没有声称容器冒烟通过。数据库、静态构建、单测及真实浏览器验证均不依赖该守护进程。

完整原始测试结果保存在 release-artifacts/final-audit-20261002/，不把浏览器截图、数据库、凭证或完整数据快照提交到源码分支。
